## Releases de demonstração

A sequência usa arquivos novos, um PR por etapa, sempre develop → main:

1. `04_Create_Test_Table.sql`: cria `ws4_demo.teste_deploy` com id identity, descricao, created_at e active.
2. `05_Alter_Test_Table.sql`: adiciona observacao e altera descricao para varchar(120).
3. `06_Alter_Test_Table_Drop_Column.sql`: remove somente observacao.

Cada script tem um contrato de estrutura em consultas/testes. Os modelos de DDL em consultas/modelos são alternativas; não fazem parte do catálogo ativo até serem copiados e renumerados.

## Conferência no PostgreSQL

```sql
SELECT versao, arquivo, commit_sha, execucao, aplicado_em
FROM ws4_controle.versoes ORDER BY versao;

SELECT column_name, data_type, character_maximum_length, is_identity
FROM information_schema.columns
WHERE table_schema = 'ws4_demo' AND table_name = 'teste_deploy'
ORDER BY ordinal_position;

SELECT id, descricao, created_at, active FROM ws4_demo.teste_deploy;
```

A tabela de amostra fica vazia e disponível para consulta. A validação funcional de inserção deve usar transação e ROLLBACK, sem deixar registros de teste. Uma sequência pode avançar mesmo após ROLLBACK; isso é comportamento esperado.

## Proteção e aprovação

Depois de tornar o repositório público, a proteção nativa da main ficou disponível. Ela exige PR, branch atualizada e quatro checks, aplica-se aos administradores e impede force push/exclusão. O laboratório permite o merge manual pelo proprietário depois dos checks, sem exigir uma segunda conta. O [processo corporativo](../processo-release-bd.md) descreve card, identidades individuais, revisão por outra pessoa e aprovação de release como referência de equipe.
